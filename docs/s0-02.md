# S0-02 — Charger le modèle via ONNX Runtime depuis Rust, CPU (carte TW-6)

Date : 2026-11-17. Statut : **critère atteint** — inférence CPU fonctionnelle depuis Rust.

## Chaîne validée

```
tokens i64 (dumpés par la chaîne Python de référence)
  + style f32 [1,256]  + speed f32 [1]
  → crate ort 2.0.0-rc.15 (EP CPU)
  → kokoro-v1.0.int8.onnx
  → f32 24 kHz → WAV
```

Le prototype réplique exactement `_create_audio` de kokoro-onnx : pads 0
autour des tokens, style indexé par la longueur de tokens. La phonémisation
reste côté Python pour cette carte (goulot traité sur la carte TW-7).

## Résultats mesurés

| | Python (kokoro-onnx, référence) | Rust (ort 2.0.0-rc.15, release) |
|---|---|---|
| FR — af_heart, 102 tokens | 6,06 s audio, RTF 0,52 | 6,70 s audio¹, RTF **0,38** |
| EN — af_heart, 88 tokens | 5,03 s audio, RTF 0,56 | 5,67 s audio¹, RTF **0,38** |
| Chargement du modèle | — | **1,29 s** |

¹ durées non tronquées (trim non implémenté côté prototype) ; les durées Python
sont après coupe des silences, d'où l'écart, sans incidence sur le RTF.

Le RTF Rust inférieur à Python tient probablement à moins d'overhead et aux
optimisations du graphe niveau 3. **Marge CPU confortable : RTF 0,38 sur la
machine de référence, quasi 3× temps réel.**

## Risque levé et suite

- **« Opérateurs ONNX incompatibles » : risque levé.** Les opérateurs de
  l'export int8 (dont les Q/DQ de quantification) passent tous sous l'EP CPU
  de ONNX Runtime 1.x livré par ort.
- Suite immédiate : carte TW-7 — résoudre la phonémisation FR/EN **depuis
  Rust** (espeak-ng liable sous GPL-3.0, cf. `docs/licences.md`), puis brancher
  les tokens sur cette chaîne démontrée ici.
- Pour le futur cœur : attention à l'API ort 2.0 (Environment explicite,
  session mutable, extraction `(shape, data)`) — API encore en RC, à figer
  dans `Cargo.toml` du projet final.
